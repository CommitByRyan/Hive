# Python 原型 → Rust 重构：差异分析

> 依据：`docs/reference/HIVE_BUILD_SPEC.md` 的模块契约（§6）、Agent 协议（§7）、工具与安全边界（§8）、HTTP/SSE（§9）、前端（§10）。
> 结论：**保留产品行为，重写执行内核**。逐行翻译会继承原型的串行假设与内存态审批，达不到“抗打”。

## 1. 模块映射

| Python 模块 | 原型职责 | Rust 归属 | 决定 |
|---|---|---|---|
| `config.py` | 环境变量 + 默认值 + 模式切换 | `hive-config` | 保留语义，改为强类型 + 启动期校验；不做隐式全局单例 |
| `db.py` | SQLite DDL、任务/事件读写 | `hive-store` | 重写。不复用旧 DDL；单写者 + WAL + 短事务 |
| `events.py` | 事件产生与广播 | `hive-events` | 重写。持久化优先，内存订阅只是加速；`seq` 游标补齐 |
| `llm.py` | OpenAI 兼容调用 | `hive-llm` | 重写。补流式增量、tool_call 拼接、usage 校准、错误分类 |
| `tools.py` | 工具实现与沙箱 | `hive-tools` + `hive-policy` + `hive-workspace` | 拆分。策略与执行分离，路径/网络/Shell 可独立测试 |
| `approvals.py` | 审批请求与决定 | `hive-policy` + H02 持久化 | 重写。内存轮询 → 持久 pending + CAS 决策 + 超时扫描 |
| `agents.py` | 角色、工具白名单、规划器、单 Agent 循环 | `hive-agent` | 保留协议，重写上下文与工具调用路径；Agent 不直接执行工具 |
| `runtime.py` | 任务执行主循环 | `hive-runtime` | 重写。串行循环 → DAG 就绪队列 + 租约 + 取消 + 预算 |
| `scheduler.py` | 定时任务 | `hive-runtime::scheduler` | 保留语义，补错过触发补偿与幂等 |
| `server.py` | HTTP/SSE/审批/定时路由 | `hive-api`（H08） | 保留路由与事件语义，改为 `seq` 断线补齐 |
| `__main__.py` | CLI 入口 | `hive-cli` | 保留子命令，增加 `doctor` / `migrate` / `verify` |
| `web/*` | 单页控制台 | H08 控制台 | 保留页面结构与视觉，状态改事件驱动，不再整页轮询 |

## 2. 必须丢弃的原型做法

| 原型做法 | 为什么不能带进 Rust | 替代 |
|---|---|---|
| 单一长生命周期数据库连接、长时间持锁 | 并行节点会互相阻塞，崩溃后状态不可信 | 每次操作短事务；单写者串行化；WAL |
| 审批存在内存里、靠轮询推进 | 重启丢审批，多客户端看不到一致状态 | `approvals` 表 + 单事务 CAS + 超时扫描 |
| 任务串行接力 | 与“高性能多 Agent 协作”直接冲突 | DAG 就绪队列 + 并发上限 + 租约 |
| 工具结果整段塞进对话历史 | 上下文爆炸，无法重放 | 事件放摘要 + artifact 引用 |
| 字符串拼 Shell 命令 | 注入面无法穷举 | argv 数组 + 白名单程序 + 默认禁用 |
| 事件 kind 是自由字符串 | 前后端各自解释，无法演进 | 封闭 `EventKind` 枚举 + payload schema |
| `agent.thought` 这类以 agent 命名的事件 | 与 Node 层级不一致 | 统一 `node.*` 命名 |
| 前端定时整页刷新 | 丢中间态，无法断线补齐 | SSE + `seq` 游标 |

## 3. 必须保留的产品行为

- 角色与工具白名单：每个 Agent 只能看到被授权的工具。
- 规划器协议与降级路径：规划失败要有 `plan.degraded`，不能整单失败。
- Demo 大脑：无 API Key 时仍可跑通全链路，便于验证内核。
- 单 Agent 执行协议：一次 Turn 内的模型→工具→结果循环语义不变。
- 审批语义：高风险工具必须人工确认，且能看到将要执行的参数。
- 定时任务：cron 表达式的用户可见行为不变。
- 前端信息架构：Mission 列表、节点进度、事件流、审批入口不变。

## 4. “像 Codex 一样抗打”的四个硬指标

| 指标 | 机制 | 落在哪一步 |
|---|---|---|
| 可恢复 | 状态与事件同事务、租约过期回收、`needs_recovery` 三态判定 | H02 建基础，H05 做调度恢复，H09 做启动扫描 |
| 可取消 | `CancellationToken` 贯穿模型流、工具执行、子进程树 | H04 打通单节点，H05 传播到 DAG |
| 可审计 | 每次工具调用三段事件（intent/started/result）+ 审计哈希链 | H03 建审计，H09 做导出 |
| 可接管 | 租约 token 与 attempt 分离、CAS 提交、重启换 runtime instance | H02 建表与 CAS，H05 定领取算法 |

判定标准：强杀进程后重启，任何已确认副作用的节点不得重跑；任何状态不确定的节点必须进 `needs_recovery` 而不是自动重试。

## 5. 与原型的兼容边界

- 不自动迁移旧 Python SQLite；只提供一次性导出（Mission 目标、消息、产物元数据）。
- HTTP 路径保持 `/api/*`，但事件内容升级为 v1 封套；旧前端不保证免修改。
- CLI 子命令名尽量保持，新增命令不破坏旧脚本。
- Python 的 `.env` 读取习惯保留，但必须显式 `Config::load()`，不在库内部读环境。

## 6. 代价

- Rust 版首版功能会比 Python 原型少：先保证可恢复与可取消，再补体验细节。
- 状态机与表结构更复杂，H02/H03 的测试量显著高于原型。
- 单进程仍是单点：进程崩溃会中断所有运行中任务，只能靠恢复而非高可用解决。
- 不引入分布式调度；跨机器需求出现时再按协议边界拆分，而不是提前微服务化。
